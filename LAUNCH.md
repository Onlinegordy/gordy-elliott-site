# AT CAPACITY build and release

## Application

The Next.js application serves the client portal and coach administration at `https://app.onlinegordy.com`. The iOS and Android projects use the hosted portal with native integrations. App identity and native versions are defined in `config/app-identity.json` and `config/android-release.json`.

## Local development

1. Install the locked dependencies with `npm ci`.
2. Configure `.env.local` for the intended development backend. Keep secret values outside Git.
3. Run `npm run dev`.
4. Before release, run `npm run test:release-contracts`, `npm run build` and the checks relevant to the changed integration.

Core runtime configuration includes `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, server-only `SUPABASE_SERVICE_ROLE_KEY` and canonical `NEXT_PUBLIC_SITE_URL`. Configure the existing provider credentials for enabled AI, email, calendar, wearable and push integrations in the target hosting environment. Never put server credentials in `NEXT_PUBLIC_*` variables. Preserve existing signing and push identities across updates.

The approved coaching knowledge in `data/brain/` is product content. Preparation/import commands require separately supplied, reviewed input; they are not normal application startup commands.

## Database and deployment

Schema and policies live in `supabase/`. Before applying a change, verify the intended project and existing migration history; apply only the reviewed pending migrations in the required order. Do not replay historical bootstrap SQL against a live database. Supabase CLI linking state is local and regenerated by the CLI.

Deploy the reviewed commit through the existing Vercel project. Confirm the production deployment is READY and its Git SHA and `app.onlinegordy.com` alias match. Check public login/privacy/support pages, signed-out portal redirection and authenticated access using a permitted test account. Check the affected client/coach journey before releasing a functional change.

Use the existing last-known-good Vercel deployment for a web rollback, then verify the domain and affected journey. Revert faulty code through a new commit; do not force-push main for a routine rollback. Database rollback requires a separately reviewed forward repair.

## iOS hosted-portal release control

The App Store binary opens the hosted portal at `https://app.onlinegordy.com/portal`. A Vercel rollback therefore changes hosted content without replacing the signed binary.

Use `npm run ios:sync`, `npm run ios:preflight` and `npm run ios:archive` with the configured Apple signing identity. The archive script records its source revision and refuses to overwrite an existing archive. Listing inputs are in `docs/app-store-metadata.md`; verify them with `npm run verify:app-store-metadata`.

Before the final physical-device walkthrough, record the tested Vercel deployment ID, Git SHA, iOS version/build and reviewer-fixture check. Any later portal deployment invalidates that walkthrough and must be smoke-tested again before submission.

An App Store binary cannot be rolled back after release. Ship a corrected higher version/build for a released native defect; do not replace an accepted archive in place. Keep review credentials and release contact details in App Store Connect.

## Android

Follow `docs/android-release.md` for SDK, signing, Firebase and bundle commands. Physical-device checks must cover login, training, messages, uploads, optional integrations, notification lifecycle and app links before store release.
